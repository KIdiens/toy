# ADR-014：AI 播放工具按会话准备，安全回复结束后串行执行

日期：2026-10-24。状态：Implemented（本机软件验证）。

## 问题

`play_action` 仅检查白名单便返回 `scheduled=true`，没有进入运动队列；`play_content` 未装配回调也会成功返回。另一个断点是：AiRouter 已将不合格输出替换成固定安全话术并合成，但 net worker 因 `blocked=true` 丢弃这段安全语音。

直接把工具回调接到设备也不合适：模型仍在网络线程中，后续输出尚未审核，用户也可能已经取消或换角色。工具接受与设备完成必须分开表达。

## 决定与实现

- `tool_scope.py` 用 ContextVar 隔离每轮请求守卫、角色版本及待执行效果。ASR、LLM、工具、TTS 的阶段边界检查请求是否仍有效。`AiCancelled` 是正常取消，不增加工作线程故障计数。
- `ToolPerformer` 在网络线程准备白名单动作快照或本地音频快照；本地文件须为有效的单/双声道 16-bit PCM WAV，并通过峰值/削顶检查。缺失文件或未装配执行端口明确拒绝。
- 未加载公仔角色仍可通用问答；安排动作或本地内容计划则须有可核对的角色与版本。
- 工具回执表示 `accepted=true, scheduled=false, pending_reply=true`，不称设备已经开始或完成。AiRouter 只有在最终回复审核通过后，才将准备好的 `performances` 随 `AI_DONE` 交给核心。已列明的直接提前完成说法在 TTS 前改成将要执行的确认；这不是任意语言、任意句式的完整事实性保证。
- 先播放审核后的回复，收到正常 `PLAY_DONE` 才执行第一项。动作走现有 `PERFORM_PRESS`/`PLAY_ACTION`；本地音频走内部 `LOCAL_PLAY`（IDLE→SPEAKING），不重新录音或调用网络。每项正常完成后才派发下一项，保持请求顺序。
- 正常完成会进入 IDLE 并增加会话代数，计划在同一次核心派发内更新自己的预期代数；外部取消、换角色、配置变化、故障和音频失败不继承计划。STOP 在 THINKING 期间也取消等待，防止旧模型结果返回后又开播。旧代数的音频失败不得清掉新计划。
- 一轮最多准备 8 项播放任务。超过上限、参数被拒或两轮工具预算结束后仍未得到最终答复，整份播放计划不执行。同一非空 call_id 的重复请求复用结果，不重复准备任务；同编号换参数则拒绝。
- `refusal_ready` 只标记已替换为三种固定安全模板、且已取得合成片段的拒绝回复。它可以进入 SPEAKING；未具备安全回复的失败仍走 AI_FAIL。拒绝回复不携带播放计划，也不能解除故障锁定。

## 取舍与边界

核心只调度准备好的数据，不读动作文件、不做网络或音频解码。音频与动作在本实现中串行执行；这次不交付 M9 的音画并行同步，也不证明 C6 的 <100ms 实测指标。

守卫阻止取消后的后续调用，不声称能够强制终止已经执行中的同步云请求，也不自动回滚已经提交的数据库事务。真实云延迟、费用、内容质量和实物安全继续待验收。项目未附真实故事素材；回归使用临时目录生成的音频与动作夹具。

## 验证

- `tests/unit/test_ai_tool_scope.py`：阶段取消、并发隔离、执行端口缺失不假报成功。
- `tests/integration/test_ai_performance.py`：计划串行、审核拒绝、取消/换角色/配置变化、重复调用、预算上限及提前完成表述的有限句式对照。
- `tests/integration/test_ai_tools_threads.py`：真实领域线程与 pyserial/TCP 模拟 MCU；核对接收端 ARM/FRAME/STOP、播放顺序、串口不重叠、回复/运动中断、阻塞模型与音频设备失败。
